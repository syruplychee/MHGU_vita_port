# 整帧主要成本查实与后续接管依据

日期：2026-11-05。基点 `8f42a38`，调查分支 `codex/frame-cost-audit`。
证据：锁定二进制/源码 L0、宿主 L1、Vita 构建 L2、有限村庄 L3；无 L4/L5。

## 1. 先给判断

当前村庄性能的首要问题是**纹理驻留和重复处理**，不是纯命令解释，也不是某个
清屏函数的一次等待。对话近景的正式参考窗口中，纹理比较、转换、保存和选槽自身
合计约 **42.9 ms/帧**；纯 entry/dispatch/MME 自身合计约 **7.9 ms/帧**。

原游戏上游已经实际计时，约一百多毫秒的队列函数主要在同步进入平台桥/后端，
不能把它整体当成可省掉的原游戏 CPU 时间。只把原 ARM 控制流程翻成 C，再继续产生
相同 NVN 命令、走相同资源管线，不会省掉这部分大头。

后续第一优先级应进入**原游戏资源创建、写入、版本和释放**，建立有可靠失效依据的
原生 GXM backing；第二优先级是从原游戏完整绘制记录直接交付有类型的后端请求，
同时停掉相应旧编码、MME 和状态重建。不能继续只在 NVN 表面少包几次调用。
用户已明确批准这一深度，授权写入 AGENTS 和 ADR 0028；玩法逻辑仍保留。

这里的 backing 就是 GPU 实际读取的那份内存；资源版本记录“这份数据什么时候真正
改过”，从而在有证明的前提下保留转换结果。直接请求则把原游戏已经准备好的目标、
程序、顶点/索引、纹理、uniform 和状态交给后端，省掉先编码再拆回这些字段的往返。

## 2. 这次怎样避免重复计时

“包含时间”是函数进门到出门；“自身时间”扣掉已经测到的直接子调用。子调用还可
继续分层，但每份时间在主表只出现一次。两个线程的墙钟不能相加。

新增 22 类单 worker 嵌套计时，计全部成功/提前返回；错误、残缺快照、累计倒退和
self/root 不对账都会拒绝。每 32 个 present 同时记录完整累计、已有 GXM 成功 batch
细分、纹理格式与查询原因。root journal 的区间和必须等于累计 root 差。

原游戏四个 A32 函数保留原执行，只包围计时：`3DA8FC`、`BBE154`、`BBE66C`、
`BC0874`。每线程独立嵌套，并单列同步进入平台桥的时间。所有时间使用同一进程时钟。
最终用区间并集，而不是线程耗时相加：

```text
整帧 = worker 已测时间
     + 原函数区间中不与 worker 重叠的部分
     + 两者均未覆盖的时间
```

参考窗口覆盖率约 **99.1%**；未覆盖约 1.2 ms/帧，保留为未归属，不冒称游戏逻辑。
这说明主要墙钟成本已经闭合，**不等于测到了所有线程 CPU 周期或 GPU 硬件执行时间**。
细节见 ADR 0027/0028。

## 3. 测试条件、窗口与工具开销

- Vita3K d7edcbe9，OpenGL，540p，静态 shader index `ed60817f…`、364 variants。
- 模拟器 SHA256：`dd68489a2ddb1cc7910712c2eb5925a0b2af70c507f6703a28d3a43815479d13`。
- 锁定 1.4.0 原游戏、受保护的同一测试存档；不用 GPU live capture/SurfaceReadback。
- engine A/B 固定 mode 4：原游戏 root trampoline + 当前默认 deep 纹理路径；不启用
  native C root、shared、idle-recycle 或 deferred-clear。
- 新 frame-cost 在同进程按 0/1/0/1 切换。正式对话窗口选择进程时钟 465–505、

  这些窗口避开截图和有界资源捕获；每段完整直方图均至少 128 帧。

## 4. 不重复相加的主成本表

参考：`frame-cost-resources-20261105` 前两段固定原村长对话页，共 800 个帧间隔。
以下分组由同端点的 self 相加，最后两行由区间并集补齐，合计约 134.26 ms。

| 部分 | 对话近景 ms/帧 | 移动后宽视角 ms/帧 | 这里实际在做什么 |
|---|---:|---:|---|
| 纹理处理 | **42.87** | **50.92** | 近景：raw 查询/比较 13.73、转换/反平铺 19.22、保存 8.65、选槽/分配自身 1.27 |
| GXM 准备、调用与场景自身工作 | **21.10** | **34.57** | draw、flush/clear 自身；已扣通知和日志子项 |
| 真实 SDK 通知/Finish 阻塞 | **20.21** | **27.40** | 通知及 Finish API 阻塞；不是 GPU 总执行时长 |
| 请求准备、索引窗口与框架自身 | **11.76** | **15.39** | 状态、索引窗口、cbuf 地址、资源元数据，加请求调用前后等 |
| 已有工作日志 | **10.54** | **12.40** | glog/slog 的格式化和写入；从父项扣除，不再次相加 |
| entry / dispatch / MME 自身 | **7.89** | **10.63** | 不含子 draw、纹理和 GXM |
| 原函数区间中不与 worker 重叠的部分 | **18.71** | **23.39** | 帧阶段/原编码、桥接空隙、调度等；不能全部叫游戏计算 |
| 两者均未覆盖 | **1.17** | **1.12** | 新统计输出、未插点路径和边界空隙等；明确保留 |

宽视角在对话确实结束、角色移动及镜头改变后测量，窗口为进程时钟
`645121502..797026975` µs，864 帧，覆盖率约 99.36%。纹理查询自身升到约 23.73 ms，
转换约 16.40 ms，保存约 8.94 ms；请求数约 631.50/帧，miss 约 97.31/帧，仍全部为
absent，比较请求长度约 358.54 MiB/帧。取景变化后纹理和 GXM 成本都增大，主要排序
保持，不能只用较轻的对话近景代表村庄所有视角。

同端点直方图：对话两段 p50 为 133–134 / 132–133 ms，p95 为 153–154 / 150–151 ms，
p99 为 177–178 / 165–166 ms；宽视角 p50 173–174、p95 196–197、p99 226–227 ms。
分位数是 1 ms 桶范围，不是精确单帧时间。

三组要防止误读的数：

1. 纹理 store 的**包含**时间还包括池满触发的 flush/wait。上表只放其自身 1.27 ms，
   真正通知阻塞已经放到 20.21 ms 中，不能再把 store 包含时间加上去。
2. 纯命令处理约 7.9 ms，不是旧 command_dispatch 包含时间的一百多毫秒。
3. GPU 可以与 CPU 工作重叠。等待 20 ms 不能证明 GPU 全帧只工作 20 ms，也不能证明
   GPU 不重；本报告没有 GPU 内部时间戳、shader 单元或真机计数器。

带旧等待原因计时的第二轮，在与该轮成本表完全相同的 736 帧端点里，texture-pool
触发通知阻塞约 **12.43 ms/帧**（11 次真实 wait/帧），clear 约 **5.56 ms**（约 4 次），
submit-end 约 0.78 ms，其余约 0.35 ms。它是该轮约 19.11 ms 的原因拆分，不再加到
上表；无旧 play-perf 的参考轮不能用全零旧计数冒充原因消失。这进一步支持先解决
纹理空间和生命周期，而不是继续只移动清屏等待。

## 5. 纹理大头的原因已查到哪一层

正式参考窗口平均约 472.67 次纹理请求/帧，388.96 次 hit、83.70 次 miss。真实查询
原因计数中，miss_changed=0、miss_gpu_only=0，全部 miss 当时都没有可用匹配 raw
驻留版本。成功比较的请求范围合计约 237.55 MiB/帧；这是比较长度，不是硬件带宽。

另用每个 profile epoch 前 16 个 present 范围做有界元数据捕获，正式耗时窗口排除它。
排除各段首尾不完整帧后，共 40 帧、89 个完整 key；每帧约 83.28 次 miss，全为 absent，
其中约 81.05 次/帧在更早捕获帧已请求过相同 key。不是大量首次出现的新资源。

这 89 个已观察 key 的 raw 合计约 65.90 MiB、解码结果约 66.01 MiB。它是跨捕获段
集合，不应直接冒称所有版本同时驻留；但其中 **10 张 1024×1024 RGBA8** 在捕获的
每个完整帧都重复 miss，每张 raw 4 MiB、输出 4 MiB。仅这一组就需 **80 MiB**，已
经超过当前合并 raw+decoded 的 **64 MiB** 池，尚未算压缩块、骨骼浮点纹理和其他资源。

因此“不断重新找不到 → 再反平铺/复制 → 申请安全槽 → 必要时等待 GPU 退休”有直接
容量与运行证据。已有 deep 路径已经把 decoder→staging/upload 的中间复制降到 0，
但为逐字节身份比较保留的 raw 快照以及 miss 后重新转换/保存仍然昂贵。

这里的 64 MiB 是项目继承原 48 MiB decoder + 16 MiB upload 的合并预算，不是
CDRAM 容量或 GXM 的硬件限制。源码 L0 确认：`gxm_texture_chunk_create` 申请的是
`USER_RW_UNCACHE` 主内存，再通过 `sceGxmMapMemory(...READ)` 供 GPU 读取；当前
decoded 已直接从映射主内存绑定，不是每次必须上传 CDRAM。raw 快照仅供 CPU 比较，
不绑定 shader；但 region provider 忽略 `gpu_read`，使 raw/decoded 共用上述 uncached、
GPU-mapped chunk。将 CPU-only raw 拆到 cached 主内存、只映射 decoded 是另一个
可测试切片；尚无 A/B 证据证明其收益。拆开存放不会自动消除双份总占用，映射也不会
转换原游戏纹理布局；缓存可见性、源写入和 GPU 持有期仍须分别处理。

这里还有一个必须保留的边界：**同 key 重复，不能证明被淘汰后源像素没变。**
没有旧 raw 时无法做那次比较，所以不能据本报告按地址跳过校验。要安全地去掉大块
raw 副本，必须深入原游戏资源创建、写入、更新和释放，建立可靠版本/失效依据；
动态矩阵、骨骼数据和流式资源尤其不能照静态纹理处理。

稳态旁证：两段相邻计数窗口的 kernel alloc/free、中间 staging/upload memcpy、
direct_fail、quarantine 增量均为 0。说明这次的大头不是尚未解决的逐纹理系统申请。
这些计数窗口和主表端点不完全重合，只作旁证，不混算毫秒。

## 6. 索引、GXM 与日志的具体范围

`frame_submit_draw_impl` 的窗口扫描约 4.2 ms/帧。带旧细分的第二轮，在成功 batch
路径中，GXM 的 index 准备约 7.6 ms/帧，包含真实重映射/扩宽/复制和 restart/strip
处理。前一处求范围、后一处生成 GPU 所需索引，职责不同，不能简单删掉后一遍。

现有代码已经复用 restart 数量；零 restart 会跳过不必要的 join/marker 路径。同宽、
window_first=0、无 restart 的情况已有 bulk memcpy。下一步要查索引资源的版本、
原生 GPU 可读地址和预生成结果，不能把“还有两处遍历”直接叫作两处重复计算。

第二轮成功 batch 的颜色和深度绘制各约 220 次/帧，GXM 准备分项中 index 显著高于
单纯 vertex copy、sampler 元数据和 uniform 预算检查。该表包含在 GXM 总量内；旧细分
含自身日志，且不覆盖失败/legacy draw，因此不再加到主表。

第三、四轮把工作中的 glog/slog 单独计时，约 10.5–10.7 ms/帧。新增 root journal 和
整套快照本身不在这项里；它们留在工具开销/未归属中。说明现有工作日志确实是一项
可独立验证的成本，但还没有执行“关掉日志就一定提速这么多”的实验。

两段参考旁证中已有 stage 3 拒绝分别增长 12/18；stage 9–13 无新增拒绝。既有反馈
效果省略路径也仍存在。没有借这次计时新增跳 draw 或绕过失败；也不能把有限窗口
“未见新增黑块”说成全部原绘制都已支持。

## 7. 原游戏二进制已经追到的位置

全部地址为 main 模块偏移，不可硬编码为运行时绝对地址。输入/原字节/ABI 契约见
`config/patch-plans/game-cost.json`。反编译得到的角色名称只描述用途，不冒认原始类名。

| 原位置 | 已证实的内容 | 证据/用途 |
|---|---|---|
| `B8692C` | 循环中调用 `BBE154`，再调用两个对象的虚表 `+1C` | L0；真实 caller LR 对应这条循环 |
| `3DA8FC` | 通过大量子系统虚表组织帧阶段，末段调用 `BC0874` | L0/L3，原函数已计时；不是所有玩法逻辑 |
| `BC0874 → BBE66C` | 帧尾路径进入原队列记录/提交 | L0/L3，包含后端同步处理与呈现 |
| `BBE66C → BBE9C8` | Begin/End command 记录、公共队列编码、随后提交 | L0/L3；不能把包含时间当原编码自身 |
| `BBE9C8` | 原公共队列消费者，调用状态/材质/布局和 draw 编码 | 原字节 L0，已有对照 L1/L3；原 C 替换仍继续走 NVN |
| `BC2904` | 准备/汇集队列，向 `ctx+43BB10+selector*4` 写游标、向 `+43BB18+selector*4` 写数量 | L0，具体 producer 边界，位于公共消费者上游 |
| `BC2F94` | `BC2904` 的直接子调用；枚举 `+43BB74/+43BB78` 工作，构建状态记录 | L0，继续读 producer 数据及依赖的切入点 |
| `BC3418` | 同一 producer 的另一直接子调用，构建状态/参数记录 | L0，未单独计时，不按函数长度猜成本 |
| `BC399C` | 上游较大的状态组织函数，有来自 `3DE9C8` 的调用和虚表数据引用 | L0，间接调用/共享尾部仍有缺口 |

运行中对话参考第一段：`BBE66C` 包含约 122.05 ms/帧，其中约 118.97 ms 在平台桥，
自身扣桥后约 3.08 ms；`BC0874` 扣子函数与桥后约 1.62 ms；`3DA8FC` 的 self 扣桥
约 8.48 ms。它们仍是墙钟，不能作为 CPU 周期，更不能再与 worker 表相加。
`BBE9C8` 原编码时间由已有 ENGINE_PREPARE_TIME 独立列在证据 JSON。
其近景均值约 **0.885 ms/帧**、约 150446 个连续编码字节/帧；宽视角约 **1.097 ms**、
198079 字节/帧。所选窗口 growth 为 0，不把换块错误记成零字节。这直接限制了仅
重写原编码函数本体的收益空间；要覆盖下游大头，必须同时改变后续资源和请求路径。

静态工具重新从锁定 NSO 解压，并核对三个 ELF LOAD 段逐字节相等。旧 Ghidra 库的
no-return 误传播已发现并在只读会话处理；没有拿被截断的 44 B 假函数体作结论。
producer 的静态角色没有被冒充为实测热点；下一刀仍按上面的成本和真实写入关系选。

## 8. 接下来按什么顺序做实验

| 顺序 | 应做的切片 | 已测成本范围/收益上界 | 通过条件 |
|---|---|---|---|
| 1 | 追原游戏纹理/缓冲的 owner、创建、写入、释放；为稳定版本保留原生 backing | 覆盖约 43 ms 纹理直接成本；不是承诺全省。池等待的变化不能再加一遍当收益 | 可靠失效，动态资源不误复用，旧 GPU 引用仍保留，图像与整帧同时验收 |
| 2 | 从完整原绘制记录建立 typed 请求，跨过 NVN 编码→MME→重复状态恢复 | 纯命令约 8 ms，另有元数据/请求重建；只翻译原函数控制流程不足以覆盖这些成本 | 对应旧编码/解析停止执行，顺序/全部动态字段一致，有有限原队列对照 |
| 3 | 索引资源版本化、共享原生索引或保留转换结果 | 前后约 12 ms 涉及索引，但必要扫描/转换必须保留，不能声称全部可删 | width/restart/base/window/VertexId、对齐和 GPU 完成条件完整 |
| 4 | 单变量降低正常工作日志 | 已测约 10.5 ms，实际收益需重测 | 保留错误/拒绝证据，不靠丢失败日志变绿；同场景 A/B |
| 5 | 根据真实资源/阶段依赖安排 GPU 提交 | 通知阻塞约 20 ms；等待可移动，不能直接删 | 证明 CPU 可见性、arena/纹理复用和 guest fence，整帧确实缩短 |

可选的快速因果实验是暂时把 64 MiB 池放宽到 128 MiB，看重复 miss 和等待是否下降。
它会增加最多约 64 MiB 内存压力，不代表适合真实 Vita，也未在本轮执行。长期方案
优先解决 raw/decoded 双份保存和版本关系，不依赖无界常驻。

后续已分别实测扩大预算和 cached raw 拆分，见 [纹理内存验证](17-texture-memory-validation.md)。
128 MiB 预算实际只取得约 88 MiB；拆分受现有 C 堆空间限制，两项均未证明提速。
不能把这些有限分配结果当作完整 128 MiB 容量或纯 CPU cache 属性的否定结论。
