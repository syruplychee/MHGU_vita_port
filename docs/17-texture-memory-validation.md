# 纹理预算与 raw/decoded 内存策略验证

日期：2026-11-05。基于 `ddae08c`，分支 `codex/texture-memory-validation`。
代码契约见 [ADR 0029](decisions/0029-texture-memory-experiments.md)，成本依据见
[整帧审计](16-frame-cost-audit.md)。证据 L0/L1/L2/L3；无真机 L4/L5。

## 1. 结论

**两个简单改动均未证明提速，保持默认关闭。**

- 合计预算从 64 改到 128 MiB：本轮平均 131.956 → 133.529 ms/帧，观测慢约
  1.19%；两对分别慢 1.59% / 0.79%。幅度较小，不认定稳定退化，但没有加速证据。
  实际 backing 仅 88.25–88.5 MiB，继续申请返回 `SCE_KERNEL_ERROR_NO_MEMORY`，
  不能把它表述成“真正提供了完整 128 MiB，仍然无效”。
- 拆分策略仍设合计 64 MiB：raw 放 cached CPU-only 主内存，decoded 保持原来的
  uncached、GXM READ-mapped 主内存。村庄稳态可双向切换，但本轮平均
  138.876 → 156.183 ms/帧，观测慢约 12.46%；两对分别慢 11.48% / 13.62%。
  实际 backing 只有 36.25–40.25 MiB，miss、转换和等待增加。

这次证实的是**当前内存布局和分配实现的实际结果**。没有证明足量 cached raw 会更慢，
也没有证明给足 128 MiB 仍不能改善容量问题。下一步应先解决能够实际提供的内存范围、
分配粒度及 C 堆竞争，再评估容量/缓存收益；资源版本化去掉 raw 快照仍有明确价值。

## 2. 单变量与运行条件

| mode | 配置 | 与基线相比只改什么 |
|---:|---|---|
| 4 | 合计 64 MiB，raw/decoded 统一 uncached mapped 主内存 | 基线 |
| 7 | 合计 128 MiB，仍统一 uncached mapped | 预算；128 槽数不变 |
| 8 | 合计 64 MiB，raw 从现有 cached C 堆分配且不映射，decoded 仍 uncached mapped | 分配位置及缓存/映射策略；不扩大 C 堆 |

三种模式共用同一个 SELF、原游戏 root trampoline、shader 包、分辨率及受保护存档。
未启用 shared、idle-resize、deferred-clear；不减少绘制、不跳过逐字节内容比较。
4/7/8 切换都在 worker submission 边界 drain、验证 GPU refs、拆旧池再建新池。

环境：Vita3K d7edcbe9，OpenGL，540p，static shader index `ed60817f…`、364 variants，
SDL 静音诊断。`play-perf`、game-cost、resource-audit、GPU live capture 和 SurfaceReadback
关闭；22 类 frame-cost 在所有正式窗口均开启。新分配统计与成本快照共用 32-present
端点。计时有探针开销，本轮没有单独测其大小，不声称是无探针默认性能。

角色停在同一村长对话页，镜头不变；NPC 和自然动画没有冻结。成功绘制/请求数仍有约
0.5%–1.4% 差异，不能把该场景叫作逐帧完全相同的工作负载。

## 4. 容量组为什么没有改善 miss

| 同端点指标 | mode 4：64 MiB | mode 7：128 MiB 预算 |
|---|---:|---:|
| 池持有 backing 范围 | 64 MiB | **88.25–88.5 MiB** |
| present 端点池内有效使用量 | 64 MiB | 64 MiB |
| 请求/帧 | 468.10 | 471.91 |
| miss/帧 | **83.57** | **83.66** |
| 查询自身 ms/帧 | 13.58 | 13.58 |
| 转换自身 ms/帧 | 17.46 | 18.45 |
| 保存自身 ms/帧 | 8.34 | 7.04 |
| 通知阻塞 ms/帧 | **20.53** | **22.29** |
| 池压力事件/帧 | 11.00 | 6.98 |
| 实际通知 wait 调用/帧 | 18.96 | 14.92 |

miss 原因全部为 absent，changed/gpu-only 为 0。压力/等待调用变少，但通知阻塞没有
随之变短，不能按调用次数估算加速。正式容量窗口无新增 kernel alloc/free，说明进入
稳态后也没有继续补足至 128 MiB。

原始日志保留 4 MiB、1 MiB、512 KiB 等申请的 `0x8002710b`（NO_MEMORY）失败。
锁定模拟器源 `ksceKernelAllocMemBlock` 会把 alignment 提升到 `size & -size`，
`alloc_aligned` 先寻找 `size+alignment` 的连续地址，再调整前部。因此一次 4 MiB
请求要先找到 8 MiB 连续地址，实际地址保留也可能超过 API 返回的可用字节。
结合已占用地址和碎片，扩大项目预算不等于系统能够提供对应大块。

`physical_bytes` 是池拥有的 API 可用 backing 范围合计，**不是硬件 RAM 占用计数器**，
不包括模拟器内部分配/对齐保留。present 端点 64 MiB 也不代表帧内从未超过 64；
候选 `pool_peak_used_bytes` 约 87.77–87.91 MiB。不能用一个端点冒充全帧峰值。

## 5. 拆分组的实际边界和两次失败

有效稳态运行先用 mode 4 完成加载，330 秒才切到 mode 8：

| 同端点指标 | mode 4 基线 | mode 8 拆分 |
|---|---:|---:|
| 池持有 backing 范围 | 64 MiB | **36.25–40.25 MiB** |
| 其中 cached raw 范围 | 0 | **16.25–16.5 MiB** |
| mapped 范围 | 64 MiB，包含 raw+decoded | 20–24 MiB，只有 decoded |
| present 有效使用量 | 64 MiB | 24 MiB |
| 请求/帧 | 467.17 | 473.83 |
| miss/帧 | **83.54** | **98.23** |
| 查询自身 ms/帧 | 14.02 | 13.07 |
| 转换自身 ms/帧 | **18.23** | **24.40** |
| 保存自身 ms/帧 | 8.61 | 6.68 |
| 通知阻塞 ms/帧 | **20.55** | **28.74** |
| 池压力事件/帧 | 11.00 | 20.46 |

miss 同样全为 absent。比较与保存略有减少，抵不过额外转换和等待。第一段拆分窗口有
一次 mapped backing 增长；其余七段 kernel alloc/free 增量均为 0。C 堆和分配失败记忆
策略限制了 raw 常驻量；这不是“相同实际容量，只改 CPU cache 属性”的纯带宽实验。

相邻静态统计旁证：八段新增拒绝均只在既有 stage 3，stage 9–13 无新增；末次
direct_fail/direct_quarantined 均为 0。这组统计并非精确成本端点，只作旁证，不混入
上表的毫秒或计数。既有可选反馈省略仍在，不能说全部原绘制均已支持。

在得到这组稳态数据之前，有两次失败，均不进入性能表：

1. `texture-memory-close-20261105`，首版 SELF `9a8ee5b…`：mode 4/7 正常运行后，
   首次切到直接新建 cached `USER_RW` 块的 mode 8，出现分配失败、强制顶点纹理缺失和
   `VP_GPU_EXECUTE_FAILED`。SDK 后续退出，不能因模拟器仍活着/最终 exit 0 而算通过。
2. `texture-memory-heap-close-20261105`，最终 SELF `f6cc348…`：从启动就选 mode 8。
   raw 的实际类型检查通过（`0x0c20d060`），但它留住约 19 MiB C 堆空间；加载期最早
   明确错误为 `VP_GPU_ENTRY_REJECT words=19825 reason=allocation-or-size`，后续
   `SDK_START status=-4`、线程池退出。该长度未超大小限制，生产 reserve 路径需要先
   `malloc` 新命令缓冲再释放旧缓冲；说明启动加载不能安全地与这份 raw 占用共用现有
   C 堆。异常处理之后的低地址写错误不是最早原因。

cached 内核块失败的地址背景已有 L0/L3 证据：模拟器 cached 从 `0x80000000` 搜索、
uncached 从 `0x70000000` 搜索；本次原游戏 arena 为
`0x88000000 + 2012217344 B`，末端 `0xfff00000`。不能把高地址空间不足叫作 PSV 的
cached RAM 容量上限。最终实现改用现有 C 堆且不扩大它：每块都核对实际 USER_RW，
不映射 GPU，释放只 `free`，不释放整个堆 memblock；没有失败后改用 uncached 的回退。

**启动、重新加载、流式场景不具备可用性验收。** 当前 mode 8 仅是诊断实验，不能作为
默认或通用策略；有效村庄窗口不能覆盖已观察到的启动失败。

## 7. 接下来应验证什么

1. 若继续验证纯容量，先做能实际提供足量 backing 的分配方案，量出 API 可用范围和
   内部地址保留；不要只继续提高宏。减少大对齐浪费/改变 chunk 粒度是候选，未执行。
2. raw 若保留，需要独立、有明确余量的 cached backing，不能默认抢 32 MiB C 堆。
   需同时验证加载时命令缓冲等既有使用者，当前稳态不能代替该验证。
3. 深入原游戏资源的创建/写入/版本/释放，减少 raw 快照和重复转换。此次没有放宽内容
   身份，也没有证实按地址直接复用安全。

Vita3K 的分配类型检查不等于测到了真机 CPU cache 收益。真机带宽/缓存、完整 128 MiB
容量、宽视角、任务/战斗、加载/流式和长时间稳定性均未验收；没有承诺任何 FPS 收益。
