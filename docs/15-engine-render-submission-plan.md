# 游戏内部渲染提交：公共入口与第一刀

日期：2026-11-03。性质：公共入口已定位，顶点布局切片已实现并进行实际对照。
实现、补丁 ABI、帧时间和采用结论见 [ADR 0018](decisions/0018-engine-prepared-vertex-layout.md)。
下面第 3–5 节保留最初的取证标准，第 6 节记录已经回答的问题；不能把最初的计划误读为
已实现完整材质系统接管，也不能把第一刀的结果外推到整个上游路线。

## 1. 目标与基线

保留原游戏已经算好的场景、模型、动画、矩阵和材质数据，向 NVN 上游追踪公共渲染
提交函数。优先省掉重复准备、命令编码和平台再解析，而不是先降低画质或扩大底层
实验开关。两词 NVN draw 标记原型只说明那个切入点太浅，不能否定引擎内部接管。

画面对照固定在黑块修复提交 `2ca906d`。本地配套版本身份见专项调查第 7 节：
VPK `fd7432b7…`、SELF `d9d28e97…`、模拟器 `dd68489a…`、静态索引 `ed60817f…`。
新实验不覆盖该冻结基线。性能数字重新测量，不能沿用修复前或旧分支的帧时间作为配对。

## 2. 已有具体入口，而非从 shader 编号猜测

本次重新从 `config/target-1.4.0.json` 锁定的 main 解压并校验三个段哈希，与现有私有
分析映像逐字节相同。NSO SHA256：
`b3935415499549adaf4c0e89822831daa175cfd456a7990791c79be3997645ef`；
解压映像 SHA256：`24c208c395c65727b21b5fa91af8381396e70cf421b0fcfee0345d8743298110`。

旧 `nvn-lr-probe1-20261102` 的真实日志记录 main 基址为 `0x85566000`。
扣除该次基址后得到以下种子；地址均为 main 模块内偏移，不是可硬编码的运行地址。

| NVN 调用 | 调用指令偏移 | 返回偏移 | 已确认范围 |
|---|---|---|---|
| BindProgram | `0xBC17D4` | `0xBC17D8` | 位于下面的公共状态提交函数中 |
| BindTexture | `0xBC21F0` | `0xBC21F4` | 与 BindProgram 同一入口中的资源循环 |
| DrawArrays | `0xBC014C` | `0xBC0150` | 前方 `0xBC0120` 直接调用公共入口 |
| SetRenderTargets | `0xBC1200` | `0xBC1204` | 阶段/目标组织的后续追踪种子 |
| SubmitCommands | `0xBBD96C` | `0xBBD970` | 命令缓冲提交的后续追踪种子 |

**首选调查入口是 `0xBC1764`。** 原字节 `f04f2de9` 为 A32 保存寄存器的入口指令，
接着分配 `0x4C` 字节栈空间。全 text 的 A32 直接 BL 扫描找到 8 个调用点：
`0xBBEE38`、`0xBBEFA0`、`0xBBF2B8`、`0xBBF3EC`、`0xBBF83C`、
`0xBBFD04`、`0xBBFFD8`、`0xBC0120`。
这是 8 个静态调用位置，不能冒称 8 类模型或 8 个独立调用者函数；间接调用、Thumb
调用与可达性未由该扫描证明。历史 LR 日志只保留每槽早期样本，也未证明当前村庄
每类 draw 的覆盖率与耗时。

此处暂称“公共状态/资源提交函数”，不冒认原始类名或完整材质系统。反汇编还确认：

- `0xBC1778–0xBC1784` 比较第二参数 `+0x10` 的旧指针与第三参数；相同会跳到
  `0xBC2214`，跳过前面的部分准备，但仍执行后续状态逻辑。
- `0xBC179C–0xBC17AC` 另比较两个对象 `+8` 的指针；不同层级已有复用判断。
- `0xBC18A4–0xBC18A8` 在资源循环中比较条目，新旧相同会跳过一段处理。
- `0xBC2210` 更新第二参数的 `+0x10`。可见它本来就维护了部分旧状态，不能以
  “Switch 游戏一定没有缓存”为前提重新包一层指针缓存。

第二参数常由调用方栈上 `sp+0x180` 传入，第三参数来自绘制记录 `+0xC`；这是寄存器
来源事实。两者是否分别为状态缓存和材质实例、生命周期多长、何处清零，仍需追踪。

以上原字节复核和调用扫描为 **L0**，历史执行记录为该旧版本的 **L3**。
REA 服务当前未配置可用 Ghidra，未产生反编译证据；本次使用仓库严格 NSO 解码器与
已有 Capstone 做只读核对。私有脚本、完整指令和种子映射保存在
`build/audit-engine-submit.py`、`build/engine-submit-seeds.txt`、
`build/engine-submit-common.txt`、`build/engine-submit-seeds.json`，不进入 Git。

## 3. 第一轮只回答三个问题

1. **这个入口覆盖多少真实工作？** 在已修复版本的固定村庄状态记录入口/调用点、
   绘制阶段、线程、draw 数及材质/资源身份。与现有平台 draw 计数和实际显示帧关联，
   不只累计 NVN 调用。先区分主颜色、深度和合成，避免按单个 shader 选小家族。
2. **时间花在哪里？** 分开统计入口包含时间、其内部 NVN 调用时间、返回后的命令解析
   和 GXM 准备。嵌套时间只能扣除一次；“入口时间 + 子调用时间”不能相加。另有
   不取证运行测开销，不能把采样/日志成本算作可优化成本。
3. **哪些数据真的可以复用？** 追第二参数的创建、清零和传递范围，第三参数的资源列表，
   以及各 bank/实际使用范围内的矩阵、材质和纹理变化。区分静态描述、每对象数据、
   每帧数据与资源写入事件；不能仅凭地址相同或一组 hash 相同认定内容未变。

取证先用有上限的计数和少量对象快照，在 host TLS 路径汇总；不在 guest TLS 下直接
调用 loader C，不照搬旧原型的单线程静态保存区。若同一命令缓冲有多线程录制，先读清
归属和提交关系，再增加记录；不能用丢记录或改变顺序来维持表面成功。

本轮交付是一张入口覆盖/时间表、一张已读清的字段与写入者表，以及一个有收益上界的
替换切片。如果该入口的本体已很便宜，沿调用者继续追对象队列和阶段入口；不因此
宣布上游接管无效，也不为了“做过优化”先加缓存。

## 4. 第一刀怎样落地

首选切片是**跨多类绘制复用的状态/资源准备结果**。选择前必须找到真实重复行为，
例如同一静态资源表反复遍历、同一描述反复展开，或者每次重建局部缓存导致旧状态失效。
能以资源写事件可靠失效的部分才跨 draw/帧保留；骨骼矩阵等动态数据继续使用当前值。

若主要成本确实是“参数已准备好 → NVN 编码 → 平台解析回参数”，就在参数完整的位置
构造 GXM 后端所需请求，逐步摆脱解码器状态快照。接管点必须同时得到目标、程序、
顶点/索引、uniform、纹理/采样器及深度/混合状态；缺字段不能从上次 draw 猜。
索引地址仍按原 ABI 的 64 位值处理，不能因当前样本高位为零就缩成 32 位。

新路径生效后，对应旧准备/编码路径停止执行；用入口、旧路径和实际提交计数证明
一份工作只执行一次。若原游戏延迟录制命令，新的请求也必须在同一个消费顺序生效，
不能在录制时提前读取以后才写好的资源。沿用后端现有资源 pin、完成通知和退休规则。

对象排序合并与阶段接管列为后续扩大方向：先证明颜色、深度、透明顺序和资源依赖允许
重排，才合并队列；先找到阶段入口及实际准备成本，才讨论整段替换。阴影降频或效果
简化是独立质量取舍，不作为这条主线已经完成的证据。

任何函数补丁在执行前都要记录锁定模块、原字节、精确覆盖范围、A32/Thumb 状态、
调用约定、被改指令的重定位方式与返回路径；本文件中的入口原字节不构成补丁方案。

## 5. 是否扩大接管的判断

- 先与当前无黑块版本做同状态画面对照，覆盖村长衣服、玩家、羊、背景 NPC、阴影和 UI；
  再做移动镜头/动画，防止静态缓存掩盖过期数据。
- 固定同一场景状态和输入，预热后交替 A/B，记录有效帧数、整帧 mean/p50/p95、
  上传/准备时间和内存峰值。不能用标题瞬时 FPS，也不能用不同对话页配对。
- 同时给出省掉的原游戏准备量、NVN 编码量和平台解析量。只少一点调用成本就继续向上
  找；若减少了多段工作且整帧稳定变快，再扩到同类绘制。
- 无硬性“必须快 20%”门槛；收益超过实测波动、画面相同、资源生命周期清楚才保留。
  需要多大范围才可能接近 30 FPS，由新测量决定。

## 6. 已完成的入口取证与替换

### 6.1 调用覆盖与现有复用

8 个直接调用点均在同一父函数 `main+0xBBE9C8` 内。父函数每次进入时清零位于
`sp+0x180` 的 `0x117C` 字节状态区；该局部复用不能直接等同于全局跨队列复用。
不能直接删除清零，因为其中还有动态资源和不同阶段的状态。

受保护的 `engine-submit-probe-fixed2-20261103` 正常运行 362.246 秒（L3），最终统计：

| 原入口统计 | 值 | 含义与限制 |
|---|---:|---|
| 调用总数 | 638,976 | 含启动/加载，不能写成固定村庄每帧值 |
| 旧对象相同 | 1,124 | 比较第二参数 `+0x10` 和当前对象 |
| 旧对象与当前对象的 `+8` 相同 | 320,988 | 已有的公共程序/布局复用层 |
| 入口包含时间 | 32.703098 秒 | 含内部 SDK 调用与取证干扰，不能与子调用重复相加 |
| 正常连续编码字节 | 150,818,296 | 缓冲增长时的跨度不计入 |
| 静态分支 0 / 2 / 4 / 7 | 103,575 / 526,564 / 3,996 / 4,841 | 四个实际运行分支；不能冒认四种原始类名 |
| 其余静态分支 / 未识别返回点 | 0 / 0 | 仅覆盖本次运行 |

### 6.2 读清并使用的字段

| 来源 | 原指令证实的内容 | 新路径怎样使用 |
|---|---|---|
| 第三参数 `+8`，随后位于 r4 | 公共程序/布局对象 | 仍由原游戏决定何时绑定 |
| r4 `+0x38` | 程序元对象 | 原 `BindProgram` 保留 |
| r4 `+0x3C` | 描述区指针 | 只读完整连续 96 字节 |
| 描述区 `+0..63` | 固定 16 个顶点属性描述 | 首次交给原 SDK 转换，之后复用实际结果 |
| 描述区 `+64..95` | 固定 4 个 stream 描述 | 同上；动态 stream 地址不在这里保存 |
| command buffer `+0x0C / +0x10` | 当前写指针 / 结束指针 | 两词记录容量检查；冷捕获要求至少 452 字节 |

96 字节完整内容是身份；对象地址和短签名仅帮助查找。原 SDK 两个编码器的完整函数
范围与哈希见补丁契约，不自行重写格式换算表。第一次执行原编码，后续相同输入直接
写入已准备记录的引用，旧两段编码停止执行。消费时在相同顺序恢复已准备的 GPU/MME
布局状态，省掉原命令展开和逐项通用分派。不能将此描述为已替换所有 GXM 绘制准备。

`engine-layout-ab1-20261103` 在同一村长对话、同一进程中执行四段原/新交替（L3）。
两个新路径阶段旧编码计数均不增长，合计命中 173,126 次；两个原路径阶段命中计数
均不增长。28 个不可变记录已覆盖该窗口，非法引用、满表与额外准备线程均为 0。
原/新各测 512 个帧间隔：158.5747 / 157.9041 ms，仅差 0.42%，不能据此宣称稳定提速。
因此继续减少新路径自身的查找和分派开销，最终结果统一记在 ADR 0018。

最终版本的第二轮同进程对照为原 158.779 / 新 160.028 ms，未证明净提速，默认不采用。
正式构建已在受保护村庄运行 352.184 秒自然退出；303,199 次命中、28 次原编码、
非法引用 0，截图覆盖村长、玩家、经过的羊与背景。自由移动/镜头未验收，不能把该窗口
当作完整村庄或玩法验收。实现可由 `engine-layout.enable` 显式启用，当前默认包不变。

任务/住宅、真机 L4、完整玩法 L5 与长时间稳定性仍是独立未验证范围。

## 完整公共准备入口实验（2026-11-04）

已将 `main+BBE9C8` 的整个队列消费和 `BC0E98`／`BC13E0`／`BC1764` 三段公共准备
实现为原生 C，并接到真实 NVN 查询／编码器。范围包含 program、两个 stage 的材质
资源、目标与状态、嵌套队列及复制／清屏；原游戏仍负责队列生产和资源创建。
启用 `engine-full.enable` 后，对应四段旧准备函数停止被新路径调用（L0）。

37 项宿主回归及 30 组合成内存与原始 A32 指令的对照通过（L1），VPK 构建通过（L2）。
单份真实队列的 6308 个接口事件和状态写回一致（L1），但 GPU 最终图像仍缺失大量
场景，不能列为画面通过或提速（L3 失败）。窗口截图对稳定包也纯白，后已改用真实 GPU
表面读回核对，避免错误归因。完整范围、补丁 ABI、对照方法、已修正错误与运行记录见
[ADR 0019](decisions/0019-engine-full-prepare.md)。实验默认关闭，当前无黑块包不变。
