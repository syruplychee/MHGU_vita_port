# 0017 角色浮点数据纹理保留 32 位精度

- 状态：已采用；L1/L2/L3 已验证，真机待验证
- 日期：2026-11-03

## 问题与决定

角色把运行时生成的矩阵放在 pitch-linear RGBA32F 纹理中。此前上传时转为 RGBA16F，
在已捕获的 125 个 draw 中，参考顶点程序的最大屏幕位置偏差为 1.08091 像素。
这不是普通衣服颜色贴图；预先把数据转成半精度仍会产生同样的舍入损失。

本地 VitaSDK 及[公开 GXM 声明](https://docs.vitasdk.org/group__SceGxmUser.html)
提供 `SCE_GXM_TEXTURE_FORMAT_F32F32_GR`，没有直接的四通道 RGBA32F 纹理枚举。
因此把每个逻辑 RGBA32F 像素存成相邻的两个 RG32F 像素，分别存 RG 和 BA。
逻辑 1024×64 对应物理 2048×64，两次 point 取样重新组成原来的四个分量。
CPU 只按 TIC 通道选择器复制 32 位位模式，不转成半精度，不修改游戏输入文件。
声明存在属于 L0/API 证据，不能代替 SGX 真机验证。

## 上传与着色器契约

- 新上传身份 `0x201`；旧半精度身份 `0x101` 保留给既有片元路径。
- cache 完整键及提示键包含上传身份，两个格式不会互相命中；分配大小、快照及
  batch 保留原有 pin/owned-retire/完成通知规则。
- 逻辑尺寸保留在 request、缓存键和 `tex0_inv_size` 中；GXM 描述符宽度为逻辑宽度两倍。
- `tex0_rgba32f_packed` 是一个 float：0 为普通取样，1 为拆分且 U repeat，
  2 为拆分且 U clamp。缺少这个参数的旧程序不能消费新数据，明确报错。
- 只接受 TIC format 1、header 2、FLOAT 分量、pitch-linear 2D、单层、无 mip；
  类型包含普通 2D 的 1 和实际角色使用的 2DNoMipmap 的 7。
  逻辑宽度最多 2048、高度最多 4096，逻辑宽度须为 4 的倍数以满足物理行对齐。
  源 pitch 至少 `width*16`，源和目标空间必须足够。
- 拆分路径只接受 point min/mag 和有效 mip-filter 编码，原生单级纹理显式关闭 mip
  过滤；2DNoMipmap 的 TSC 可以保留无效力的线性 mip 字段，不能因此拒绝角色。
  不接受 border；U mirror 会颠倒成对通道，
  暂时拒绝。V 继续使用已支持的原生寻址模式。
- 按逻辑 texel 先处理 offset 和 floor，再取两个物理 texel 的中心。U clamp 必须先
  限制逻辑像素，不能让两个通道对分别落到物理纹理边缘。

静态索引仍使用 ABI 2 的原有记录布局。改变的是 GXP 内容及反射参数契约：必须同时
生成新的 variant key、索引、VPSRES1 sidecar 和运行包，不能只替换一张纹理。
多 viewport / UINT 输入变体分别按旧 key 和 GXP SHA 替换，保留原顶点计算和输入修复。

## 实现与失败实验

`tools/shader/vertex_rg32f.py` 严格转换已验证 Cg 的独立取样赋值，保持原 UV/offset
表达式和其余算术。普通模式直接走原取样；拆分模式直接把第二次结果写入 BA，
不对矩阵分量做 lerp，避免 `a+(b-a)*1` 抵消低位。

候选曾通过 Cg 编译，但 helper 函数和部分库函数写法产生当前 Vita3K 翻译器无法处理的
调用结构。翻译器可能返回成功退出码，同时记录错误并只输出部分程序，顶点最终为零。
因此编译、CLI 退出码、GL 无错误都不足以证明画面正确；还必须检查翻译日志和有效坐标。
当前实现把操作直接展开，复用坐标临时量。不能把这段经历泛化成“所有条件分支都不支持”。

`build_vertex_rg32f.py` 检查编译器、服务和 libshacccg 身份，并检查旧 variant/GXP、
原 Cg 的精确哈希。缓存同时绑定源、helper、编译选项和工具链；失败不能生成完整包 spec。
旧包仍作为回滚基线，生成物和游戏派生源码只保存在忽略目录。

## 本地 Vita3K 的浮点上传错误

接入后即使 CPU 数据、纹理尺寸和 uniform 都正确，人物仍全部消失。临时 OpenGL
探针确认：上传参数为 `GL_RG_INTEGER + GL_FLOAT`，GL 返回错误 1282/1281，
查询到的实际纹理尺寸为 0×0；CPU 原数据非零，GPU 读回为空。这是模拟器上传错误，
不是新纹理缺少半精度压制，也不是角色没有提交绘制。

外部 `renderer/src/gl/texture_formats.cpp` 把 F32F32 与 U32U32 一起映射到
`GL_RG_INTEGER`，而 F32F32 的内部格式和传输类型分别为 `GL_RG32F`、`GL_FLOAT`。
只把 F32F32 的外部格式移到 `GL_RG` 分支，U32U32 保持整数格式。
`tools/diagnostics/patch_vita3k_rg32f_upload.py` 校验源 SHA 和唯一文本位置后生成修正，
不提交第三方完整源码或 exe。输入 SHA256：
`b75525e6ddb967f40976c14212bfcab437987e5d9d1ad8d71eb074cfbbb73345`；
生成 LF 源 SHA256：
`8d54e626c8e1a26fbaa3c49032dcff004d280ab4a2a976e488ec684e82c9629f`。

本地验证必须同时使用新 native VPK、新静态包和修正后的兼容模拟器；仅更换 VPK
无法修复模拟器的 GL 上传。此修正不涉及 GXM 真机 API，也不证明 SGX 硬件行为。
探针中的强制读回只用于定位，正式候选不包含该读回或临时 native 日志。

修正后在 Vita3K OpenGL、540p 运行 362.598 秒，正常退出。250–350 秒有效截图
显示村长、玩家和背景 NPC，未见此前整体变暗；用户同时确认当前画面已无黑点黑块。
存档、marker 和测试前 eboot 恢复均核验通过，再选择新整套产物为本地默认。
这属于 L3 场景验证和用户当前画面反馈，不是完整流程 L5 或真机 L4。

## 代价与未验证范围

每张实测数据纹理从 524,288 字节恢复为 1,048,576 字节，拆分取样需要两次读取。
CPU 不再执行 half 转换，但不能据此声称整体更快。真机速度、SGX 取样数值、全部场景、
其他尺寸和长时间运行需要单独验证。它与 ADR 0016 的两遍点积舍入修复是两个问题，
不能把数据精度修复写成全部黑块解决。具体测试结果见专项调查第 7 节。
