# 0010：SDK 锁递归与轻量入口

日期：2026-11-01。状态：实现；L1/L2 通过，L3 单次运行快路命中约 335 万次、回退约 3.2%；未证明播片提速，真机待验证。

## 背景

片头视频的解码 API 耗时远小于帧间隔。原 SDK 每次进入、退出平台锁均经过完整
336 字节上下文桥；启动及播放过程有大量这类调用。原先每层 guest 递归又对应一次
主机递归互斥体调用，增加平台调用成本。旧项目 B127–B130 有相关研究，本次逐项审查
迁入，并补宿主控制流程检查，没有直接复制旧工作区的未提交文件。

## 决定

- guest 的递归次数单独保存；只有最外层实际持有一次主机互斥体。原子 key wait
  释放这一次主机锁，成功唤醒并重新取得锁后恢复原 guest 递归次数。
- 保留 owner、pending 和槽回收检查。地址提示表命中仍核对完整地址，槽重用不会
  直接复用旧提示。争用自旋最多 256 次或 1 毫秒，随后使用原有阻塞等待。
- 阻塞超时按每次请求的 1 秒累计，最多 5 秒；不能累计内核改写后的剩余时间，
  否则连续超时可能永不结束。真实内核错误直接传播。
- 已存在的锁增加 ARM 轻量入口。入口保存 24 字节整数寄存器，通过原有 guest
  栈目录取得 executor；`VPHostBridge.user` 偏移 28 由静态断言绑定。
- 快路只处理已知主线程/worker、当前可写地址、有效槽和无争用操作。Session 按原
  dispatch 的顺序获取，忙时真实等待；只尝试 Session 会使播放时每秒数万次调用
  全部回到完整桥。Session 默认使用 [用户态门锁](0013-session-user-gate.md)。
  首次使用、guest 锁争用、未知 executor 等情况恢复原参数后进入完整桥。
  内核真实错误走专用 0x24b 错误桥，不能再次执行操作而掩盖一次性错误。
- 快路不修改 ambient guest 线程/TLS，不读时钟或逐次打印。递归、外层 Enter/Leave
  仍实际遵守原锁语义；TryLock/IsLocked 返回真实结果。
- `sdk-lock-fast.disable` 在启动时关闭轻量入口，继续使用完整桥，供同一 SELF 对照。

原 SDK 锁替换点继续使用既有 `vp022-sdk-dso.json` 的原字节和范围 SHA256；新增入口
没有增加游戏侧补丁位置，不改变模块布局。视频读回的新补丁另见 ADR 0009。

## ABI 与检查范围

本项目快路 C helper 及其整数调用链使用 `general-regs-only`；最终 ARM 链接结果中
`vp_sdk_lock_fast`、`sdk_lock_index`、`writable` 和 `vp_guest_svc_writable` 没有
VFP/FPSCR 指令，四个 ARM 入口正确切换到 Thumb C 函数。本地最大栈约 96 字节。
系统互斥体调用依赖 Vita 系统调用 ABI；导入记录不是内核实现，不能用于证明固件或
Vita3K 内部指令。后续编译器或调用链变化需要重新检查。

`tests/sdk_lock_regression.py` 从生产源文件提取实际函数和服务分支，生成 Windows
宿主模拟工程。27 组检查覆盖递归、快慢混合、key wait、超时预算、owner/pending、
内存权限、未知 executor 和真实错误。它证明控制流程和状态，不能证明内核调度或
运行速度。标准 C 宿主测试及 VPK 构建分别记录 L1/L2，运行和真机另记 L3/L4。

## 后果与回滚

轻量入口的累计次数由 `VP_SDK_LOCK_FAST` 记录。快路不采集持锁时钟，因此
`VP_SDK_LOCK_HOLD` 仅覆盖进入和退出都走完整桥的区间，不能再用于全体锁耗时统计。
运行画面、存档保护、播片内容速率和村庄回归必须单独验证；编译通过不等于 30 FPS。
