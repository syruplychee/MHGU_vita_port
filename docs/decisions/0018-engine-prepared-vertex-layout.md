# 0018 游戏公共入口复用已准备的顶点布局

- 状态：显式启用的实现已落地；重复编码已消除，但两轮对照未证明净提速，不采用为默认
- 日期：2026-11-03

## 问题与选择

沿真实 NVN 返回地址追到 `main+0xBC1764` 后，确认它在布局变化时反复调用两段 SDK
编码器：固定 16 项的 `BindVertexAttribState` 和固定 4 项的 `BindVertexStreamState`。
输入来自同一个布局描述区的连续 96 字节。编码器把它们转换成若干 Maxwell 状态写入，
平台随后又展开并逐项分发，最后得到 GXM 绘制准备需要的顶点属性、步长和实例化状态。

在公共入口 `main+0xBC17D8` 接管这段准备，保留其前面的程序绑定及后面的材质、纹理、
uniform、绘制命令和顺序。首次见到布局时，执行原来两段 SDK 代码，并保存其实际结果；
相同完整输入后续直接引用已准备的状态记录。这个切片跨多个绘制分支共享，保留原网格、
骨骼、矩阵、材质及显示效果，不做 LOD 或阴影降频。

## 准确性与生命周期

- 身份是全部 24 个原始 32 位字，不是对象地址，也不是短签名。签名和提示表只加速
  查找，每次命中仍逐字检查。不同对象的相同描述可以共用；同一地址内容变化不能命中旧值。
  地址提示命中也必须完整比较；它仅避免常见路径再计算一次签名。
- 只保存原 SDK 产生的顶点布局寄存器写入：属性 `0x458..0x467`，实例化开关
  `0x620..0x62F`，前 16 个 stream 的控制字和 divisor。顶点地址、索引、纹理、
  骨骼矩阵、uniform 数据和目标内容不进入此缓存。
- 原编码器的实现由锁定 SDK 函数范围哈希绑定，包含格式表转换。命中只省掉相同输入
  的重新转换和编码，不自行发明 NVN→GXM 格式换算。
- 原路径仍负责首次准备和所有未准入情况。只有原编码器两次保守 reserve 检查都不会
  触发缓冲增长时，才读取刚写出的连续命令区；增长、描述变化或未知写入不建立记录。
- 记录由一次 CPU 堆分配持有，64 槽有上限，进程生命周期内**不可变且不淘汰**。NVN
  命令缓冲可能重复提交，不能在第一次消费后就覆盖其引用的记录。没有 GPU 资源指针
  被此表 pin 住；CPU 表随进程退出释放，不增加 GPU 资源所有权。
- 第一个 guest TLS 身份成为唯一准备者；其余线程跳回原游戏指令，不访问可变
  查找表。owner 只在首次建立时 CAS，命中不反复加锁；空间不足、表满或重入时也
  跳回原游戏指令。只有至少余下 452 字节、两次 reserve 都不会增长时，才在 helper
  内调用原 SDK 编码器。新记录用 release 发布，消费用 acquire 读取，记录本体不再改变。
  表满时保留旧记录并执行原路径，不反复做捕获和解析。
- 新记录以私有状态方法 `0xDFF`、`0x564C0000|index` 在原命令流位置引用。
  平台只接受有效记录和 subchannel 0，并在该消费位置恢复 GPU state 与 MME shared
  两份状态。非法引用明确拒绝，不能当作已执行成功。
  已准入的方法没有 CB latch、draw 或其他副作用，消费端直接写这两份状态，不再逐项
  调用通用路由；宿主测试以原通用实现作为完整状态对照。

命中时，两段旧编码器都不执行；它们原本产生的多次通用寄存器分发也不执行。
程序、纹理、动态数据和 draw 本身仍走原路径，因此不能把这一步写成整套渲染器接管。
它也不同于旧 draw 标记原型：本次复用的是已准备的公共布局结果，而非每个 draw 到达
解码器后仍重新完成全部准备。

## 补丁与 ABI

准确的主模块、原字节、范围、两段 SDK 源码范围哈希、岛大小与参数见
`config/patch-plans/engine-layout.json`。只把 `main+0xBC17D8` 的一个 A32 指令改为
分支，跳过区间为 `[0xBC17D8,0xBC1814)`；r4 为布局元对象，r5 为 command buffer。
跳板保存并恢复 r0-r3、LR；r12 作为跳转暂存寄存器，其在这段原调用之间没有活跃值。
C helper 遵循 AAPCS 保留 r4-r11 和 SP。20 字节原生岛还包含失败返回路径：重放
`main+0xBC17D8` 的 literal load，再跳到 `main+0xBC17DC`，从原栈执行剩余 SDK
调用，保留原 reserve、回调和错误传播。literal 的来源 `0xBC23E0` 与值 `0x00C7FFBC`
单独校验，不能把有缓冲增长的原函数包进额外 C 栈后声称 ABI 不变。
helper 在 guest TLS 下只做内存、原子操作、纯解析以及原 SDK 调用，不使用 stdio、
分配或线程 API。实际目标文件反汇编检查其调用关系。

身份、函数哈希、容量和跳转距离在写入前检查；不能靠修改断言或原字节要求来接受
另一版本。`engine-layout.enable` 启动时读取；与用于计时原入口的
`engine-submit-probe.enable` 不同时使用，防止把探针开销混进候选性能。

## 验证规则

宿主测试直接使用生产缓存与生产 Maxwell 解码器，对原命令和记录路径的完整 GPU
state/MME shared 状态做字节比较，同时检查动态顶点地址不被覆盖、签名碰撞、输入
变化、旧记录重放、非法 token 和满表。构建通过不替代实际窗口验证。

整帧统计在现有 `play-perf.enable` 下运行，累计 1 ms 间隔直方图，每 32 个 present
分块输出。每条日志低于 sink 的格式化上限；缺块、被强停、原档恢复失败或无有效
窗口由 `measure_frame_window.py` 拒绝。p50/p95 是 1 ms 范围，最后一桶包含 ≥511 ms。
Present 函数自身耗时与显示帧间隔分别记录，不能混用。

同进程对照工具 `make_engine_layout_ab.py` 只生成私有构建输入，不修改生产 C 文件。
进入稳定村庄后，每 384 个显示帧切换原/新路径，共四段；`measure_engine_layout_ab.py`
各剔除头尾 64 帧，检查完整直方图、阶段顺序和原/新路径计数，保留每段 256 个间隔。
两条路径有共同的跳板开销；此对照证明的是该共同入口内替换的效果，不能称为与完全
未打补丁版本的精确加速比。启动、加载、不同对话页及强制退出轮次不参与性能结论。

首次原入口探针曾因栈重放方式错误停在加载，两个失败版本不算证据。最终把 PUSH 和
ADD SP 都放到桥接返回后的原生岛执行，保留桥接器的真实 SP 恢复约定。一次候选退出
还遇到运行器漏选 0×0 client 的最小化 Qt 主窗口；该轮严格失败保留，修正关闭窗口
选择并重跑，未降低截图或正常退出门槛。对应契约为 `engine-submit-probe.json`。

## 本轮避免重犯的错误

- 只用源地址作为键会把相同布局的多个副本装满表：首版 64 槽满后大量回退，改为
  完整内容共用后，窗口内只需 28 槽。地址相同本身不能证明数据不变。
- 每次调用加锁/原子读改写的早期版本，分进程稳定村庄 mean 曾为原 133.564 / 新
  147.239 ms；不能因为命令字减少约 21%、写入减少约 25% 就接受该版本。
  后续去锁与同进程对照也没有证明净收益，不能将锁认定为唯一慢因。
- 230 秒截图仍在加载，包含该时段的 107.44 ms 数值已排除，不作村庄基线。
- 把 512 桶放一条日志会被 1024 字节 sink 截断，不能强行解析残缺直方图；现已分八块，
  工具要求完整且累计和一致。强制结束的窗口一律不计。
- 正式包独立目录漏带构建元数据时，运行器正确拒绝启动；补齐原构建产出的元数据再跑，
  不绕过运行时资源身份检查。

未验证范围：真机 L4、任务/住宅、完整玩法 L5、羊的全部动画、全部布局工作集和长时间运行。
模拟器中未证明收益，更不能外推到 Vita 的 CPU 或 GPU 时间。
