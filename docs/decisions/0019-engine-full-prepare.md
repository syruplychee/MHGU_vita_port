# 0019：公共队列、程序／材质和状态准备的完整接管实验

日期：2026-11-04。状态：实验，默认关闭；GPU 图像验收失败，不能列为性能优化成果。

## 接管范围

本轮沿原始二进制追到公共队列入口，不再只替换两个布局编码器。保持原游戏生成的
对象、材质、网格、动画数据及绘制顺序，替换以下四段准备代码（L0）：

| main 相对范围 | 原行为 | 对应代码 |
|---|---|---|
| `[BBE9C8,BC0524)` | 遍历根／嵌套队列，处理全部记录类型，准备 stream，合并相邻 indexed draw，处理清屏／复制 | `engine_queue_native.c` |
| `[BC0E98,BC13C8)` | 颜色／深度目标切换、viewport、scissor 和目标依赖缓存 | `engine_state.c` |
| `[BC13E0,BC1738)` | blend、channel、depth、stencil、polygon 状态 | `engine_state.c` |
| `[BC1764,BC23DC)` | program、布局、两个 stage 的 uniform／texture／sampler、barrier、alpha、MSAA | `engine_material.c` |

`engine_full.c` 读取真实资源地址，使用实际 NVN 查询结果，将原 ABI 参数交给原 SDK
编码器。启用时只在根入口安装一个分支；原根函数和上述三个旧准备函数在新路径中
不被调用。调用位置及字段来自锁定 1.4.0 二进制，不靠猜结构名（L0）。原始字节、
完整函数哈希、岛布局、寄存器与 stack ABI 见
[`engine-full.json`](../../config/patch-plans/engine-full.json)。

这里“完整”限定为这四段公共准备代码。**可见性判断、队列生产、资源创建、shader
编译、NVN 编码／解析及 GXM 后端仍保留。** 现在的实现先验证能否用同一份原始数据
完整替换准备入口，尚未去掉全部“编码后再解析”，也没有证明跨对象的准备可以缓存。
不能把 C 重建本身当作省掉重复工作的证据。

原调用方 `main+BBD8D8`、`main+BBE714` 随后直接覆盖 r0，没有消费根函数返回值。
入口保持 AAPCS callee-saved 寄存器与栈约定。重建代码运行在 guest TLS 下，私有
copy／clear 不进入 Vita libc；失败通过 service `0x252` 报错停止，不静默执行旧路径。
`__aeabi_memclr4`／`__aeabi_memclr8` 和 `pow` 的 PLT→GOT→动态符号已核对；两项
游戏资源操作 `B03D98`／`B03D2C` 仍调用原函数。查询必须保留 64 位返回值。

## 检查方法和边界

1. 宿主回归共 37 项通过（L1）；其中三项测试覆盖新准备代码。
2. 将同一份合成内存分别交给新 C 和锁定原始 A32 指令，在宿主离线执行，比较有意义
   的 NVN 参数、调用顺序和持久内存写回。10 组材质、6 组状态、14 组队列，共 30 组
   有效输入通过（L1）。不把坏指针测试说成原二进制行为一致。
3. 私有扩展对照：96 组材质、192 组状态和 80 组绘制输入通过。另将第四版 VPK 的
   实际 ARM C／汇编调用边界放入 14 组队列样例，结果一致。这些仍然是有限输入，
   不是所有队列的等价证明。
4. `Unicorn 2.1.4` 只用于离线取证，不链接或携带进 VPK，不解释执行运行中的游戏。
   外部资源函数使用受控回调，数值／地址查询使用一致的受控返回；没有验证外部函数
   的完整行为。临时 stack／scratch 排除范围写在比较脚本中，持久状态不排除。

可重跑的 30 组检查位于 `tools/engine/reference/`。准备严格解码、未重定位的 main
镜像后执行（镜像哈希必须为
`24c208c395c65727b21b5fa91af8381396e70cf421b0fcfee0345d8743298110`）：

```powershell
uv pip install --python build/python-env/Scripts/python.exe -r tools/engine/reference/requirements.txt
build/python-env/Scripts/python.exe tools/engine/reference/run.py `
  --image build/graphics-binary-audit/main.bin --output build/engine-reference-new `
  --cmake build/python-env/Lib/site-packages/cmake/data/bin/cmake.exe
```

输出目录必须不存在；空用例、数量不符、指令异常、未返回或任一差异均失败。
镜像和生成的内存／事件文件只留在忽略目录，不提交游戏数据。

## 原二进制对照抓到的具体错误

- 原尾部 mask 是 `FE0001FF`，不是 `0FE001FF`；alpha 字节来自材质 word0 的
  bits 11–18，不能从更新后的状态字取。
- 两个 texture 组分属 stage 0／1；材质 bit2 强制重绑只影响第一组 uniform，第二组
  需要保留 override 之前的旧资源指针。
- 离屏目标保留缓存目标，仅当它等于当前显示目标时才换 alternate；无条件使用当前
  显示目标会绑定错误资源。
- `BBF438` 的 `STM sp,{r0,r1,r3,r5}` 写四个连续 stack word。实例绘制不能少传
  `record+24`；type2／3 的 BindVertexBuffer 第一个参数也是 command buffer。
- 普通绘制后应增加 `ctx+340F4` 的资源版本，`state+568` 是根 range 的起点。
- `state+117C` 虽在批量清零之外，随后 `BBEAB8` 明确写入 `3E`，不是未初始化值。

以上修正说明合成测试容易复制实现中的同一个错误，必须让原始指令参与对照；但修正
了这些错误、甚至全部样例通过，仍不足以宣布真实画面正确。

## 真实队列对照发现的遗漏

真实运行采集 1491 页内存（约 6 MB）。上下文在入口复制，其余对象在首次读取时保存
preimage，不是全进程原子快照；原始采集保存前 1024 个查询结果。后续缺少的纹理
handle 使用已核对的原 SDK `318888..318898` 算法，buffer address 使用 `30CDE4` 及
已核对的 memory-pool vtable 目标 `32708C`，没有用零冒充成功；已采集的 931 个
buffer 查询也与该算法一致。

初版第 2132 个接口事件有差异：原代码发出全 viewport 的 scissor，候选直接清深度。
`BC1330..BC1364` 将等于默认矩形标记的裁剪结果改为整个 viewport，候选漏掉了这
一步，会留下零面积 scissor。补齐后，单份真实输入的 **6308 个接口事件、2430 次
查询、0x1180 字节提交状态和上下文完整写回一致**（L1）。已增加零矩形回归，纳入
第 6 组状态二进制对照。这份输入未触发外部资源操作，不扩大证明范围。

## 决定

保留可审查、默认关闭的完整接管实验及离线对照工具，当前不替换无黑块默认包。
窗口截图失真曾导致错误归因；改用 GPU 最终表面后，确认候选确有场景缺失。先补齐
原 SDK 编码和底层资源取证，找第一处分歧，图像通过后再做同场景整帧对照。
目前没有净提速结论，也没有证明上游接管路线失败。

未验证：正确显示的完整接管 L3、自由移动／任务／住宅／写档、真机 L4、完整玩法 L5。
