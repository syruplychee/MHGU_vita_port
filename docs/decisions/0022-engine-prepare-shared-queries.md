# 0022：省掉共享查询往返与接管框架重复工作

日期：2026-11-04。状态：实验，默认关闭。

## 决定与执行范围

沿用原队列、材质、骨骼、网格、纹理、shader 和绘制顺序。新的
`engine-full-fast.enable` 可单独启用优化的完整接管；A/B 控制 0=原函数、1=基础 C、
2=优化 C。没有启用 marker 的正常路径不变，不替换本机无黑块稳定包。
优化／A/B 与 `VITA_PORT_ENGINE_CAPTURE` 编译组合显式拒绝；本轮优化检查使用保留了
全部真实查询返回的旧完整采集作为 oracle，不声称支持只记录省略查询后事件的新采集。

本轮实际省掉以下工作，而不是只扩大接口拦截范围：

1. 跨材质 uniform、vertex stream 和 indexed draw 共用的 buffer 地址查询，不再先
   清空 80 字节调用记录、经过通用参数封装，再进入原 SDK 查询。检查当前 pool getter
   确为锁定 SDK 的 `32708C` 后，直接读取当前 64 位 pool base 并加 buffer offset。
   不同 getter 仍执行原 SDK，保留其完整行为。
2. texture handle 使用锁定 SDK `318888..318898` 的确切位运算，不再封装并调用
   只做该运算的查询函数；保留 low word 符号扩展，不能一律把 high word 写成 1。
3. 接管框架不再每个 NVN 调用做原子加法和状态发布；各 root 用自己的栈上计数，
   完成时一次发布。统计的 last_site/slot 表示最后完成的 root，调用中间快照不用于计时。
4. 原本四字节字段读取也进入逐字节 copy 函数；ARM 构建用明确的未对齐 alias 类型
   生成原生 word/half load/store。较大的私有 copy/clear 用对齐 word 循环，尾部保留
   字节处理。guest TLS 下不调用 Vita libc；宿主映射仍使用 memcpy。

没有缓存 GPU 地址到下一帧。每次直接查询仍读当前的 pool 指针、vtable getter、64 位
基址和 offset，因此原地修改、换 pool 或资源操作之后不会使用旧值。原游戏资源操作、
所有非查询 NVN 编码、平台命令解析和 GXM 绘制保留。并未宣称已经省掉整条绘制编码
与解析路径。

## 原二进制与资源验证

严格锁定的 SDK `30CDE4`：buffer+0xC 找 pool，经 pool vtable+0x1C 调用 getter，
再加无符号 buffer+0x10。当前 getter `32708C` 仅从 pool+0x28 读 u64 后返回（L0）。
`tools/engine/reference/check_queries.py` 用实际编译的 ARM helper 与原 SDK 指令比较：
地址进位、64 位回绕、最大 offset、原地修改、pool 指针变化、getter 改为 `327094`
时走原路径，以及 handle 的负 low word 等，共 13 例通过（L1）。测试按真实 AAPCS
把第五个参数放在栈上，不把未传参数造成的测试错误归咎于实现。

同一份真实队列的原 SDK 记录包含 7881 次调用、3033 次纯查询。优化 C 实际调用
4848 次，省掉全部 3033 次查询往返（38.5% 的接口调用），但 158000 字节 GPU 命令
与原公共入口→原 SDK、运行时实际输出仍逐字节一致。571 项 program／资源描述、
0x1180 提交状态及整个上下文写回也一致（L1，真实输入来自 L3）。命令 SHA-256 仍为
`89c60ed58ff08518b444d3156d205a3904f5be59890e8e0ca5fc6a25e11ac1be`。

对照器默认仍要求完整原接口顺序。仅在显式指定 `--allow-query-elision` 时，允许优化
C 不调用已经证明纯读取／纯运算的查询；**不跳过任何非查询编码或状态差异**。资源清单
仍在实际 native buffer helper 入口采集，同原 SDK 的读取清单比较；不是放弃资源检查。
指定 `--native-entry vp_engine_full_run_fast` 选择实际编译的优化入口。

37 项既有宿主测试加 1 项 A/B 分析器测试均通过，共 38 项；30 组原二进制对照通过。
这些不包含全部玩法或显存载荷证明。实际 GPU 画面与同进程整帧结果另列，不能用接口
调用减少 38.5% 推算 FPS 同幅度增长。

## 后续应替换的准备工作

同一稳定阶段的 `VP_FRAME_BUDGET` 显示，原路径每帧约 184.5 ms 中，公共 root 不到
1 ms；命令分派包含下游工作约 163 ms，其中 draw_prepare 包含约 139 ms。纹理查询
约 12.4 ms、纹理解码约 16.5 ms、GXM prepare net 约 46.3 ms、notify 等待约 47.7 ms。
这些字段有包含关系，**不能相加成总时间，也不能把 163 ms 当纯解析开销**。

因此保留本轮有证据的查询省略及正确性门禁，但默认不启用完整接管来宣称提速。
下一处接管应覆盖原材质／资源数据到下游共享绘制准备，减少 shader pair、纹理资源
解析与准备的重复工作；只继续优化公共 root 内的小循环，其整帧收益上限很低。
这没有否定保留原游戏数据、替换准备过程的路线，而是明确大头发生在哪个阶段。
