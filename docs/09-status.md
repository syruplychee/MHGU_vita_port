| 菜单/加载 | 高于村庄，但不可作为玩法性能 | 不计入目标 |

优化历史包括：批处理、静态 shader、纹理 GOB 解平铺、上传/快照缓存、Scene 完成
流水线、clear 融合、五采样器、32 槽颜色目标 LRU。主要剩余成本在：

- GXM 调用/状态准备
- Scene 完成等待与 staging/资源生命周期
- 纹理解码与上传
- 播放器临界区/提交节奏
- 模拟器 guest CPU 调度

本分支构建已把视频读回的单平面复制降到约 0.06–0.43 ms，原 guest 播片剩余约
100–120 ms/帧的归属已由颜色转换探针和流水线标记排除平台钩子；详见第 7 节。不能
因为复制变快就断言原管线达到目标帧率。框架级原生播片不走该管线，完整片头结果为
29.974 fps，见第 8 节。

## 5. 下一阶段建议

1. **P0 原生播片收尾**：先做音频（AAC 解码、音画同步、AudioOut），再做其他影片、
   循环/退出竞态和真机 L4。原 guest 管线保留为 `native-movie.enable` 缺失或失败时
   的回退路径，不再作为 30 fps 的唯一路线。
2. **P0 回归**：本轮锁、Session、原生读回和原生播片改动影响面较大，完成村庄、
   任务入口、存档写读和截图复测后才可合并/发布。
3. **P1 任务/住宅画面**：用一次真实运行 + 定向日志确认剩余拒绝原因；修复后做完整
   场景截图与存档闭环。
4. **P2 性能**：按帧预算拆 GXM 准备、完成等待、纹理与 residual；每次只改一个有
   计时证据的方向。
5. **P3 真机 bring-up**：HW-01/02/09/03 优先；原生播片的显示内存、解码器共享和
   CPU NV12 转换另列。
6. **P4 资源流水线**：把静态包重建做成可重复脚本，并记录输入身份。

## 6. 状态更新规则

- 新结果必须写明 Vita3K 版本、后端、VPK/SELF/eboot 哈希、分辨率、场景、时间窗口。
- 单次运行不作为受控加速比例；至少给出帧时间分布和样本数。
- 修复未经过实际运行验证时，只能写“已实现，待验证”。
- 播片计时必须区分解码/合成事件、读回平面复制和颜色转换探针墙钟时间；不能把探针
  日志开销算进正式性能。
- 原生播片必须同时给出 `decoded/presented/elapsed_us/rate_milli`、影片文件、是否有
  音频和 VPK/SELF 哈希；5278 呈现帧不能写成 5280 解码帧，也不能用显示 present 计数
  替代内容帧率。
- 真机结果与模拟器不同时，以真机为准，并更新相关 ADR/文档。

## 7. 原 guest 播片 30 FPS 定位记录（2026-11-01）

最终生产构建运行（颜色探针和临时探针均关闭）：Vita3K v0.2.1 4106-d7edcbe9，
OpenGL，540p，VPK `e34e999d…`，eboot/SELF `098fdc10…`；片头窗口
t=33.8–104.3 s，610 次解码、575 次合成。

| 指标 | 观测 |
|---|---|
| 解码/合成内容事件 | 8.64 / 8.18 次/秒（目标 29.97，未达到） |
| 解码间隔 | p50 66.96 ms、p95 333.4 ms |
| 合成间隔 | p50 102.7 ms、p95 337.8 ms |
| 显示 present | 2488 次 / 103.8 s ≈ 24.0 次/秒（不是内容帧率） |
| 单次解码/合成钩子 | 5.11 ms / 0.36 ms |
| 原生读回单平面 | Y 均值 0.121 ms、UV 均值 0.063 ms |
| SDK 锁快路 | 352 万次命中，回退 110,131 次（约 3.1%） |

诊断运行补充（启用 `play-perf.enable` 与临时探针；以下数据只用于定位，
不能作为正式性能）：

- `media-color-probe.enable` 运行中 4 处补丁全部接受，`VP_MOVIE_COLOR_TIME` 为 0 条；
  当前片头不经过 `NnCodecVideoSink::ConvertYuvToRgb`/`ConvertYuvToNv12`，不能把这两个
  函数当作剩余成本。
- 播放线程大部分墙钟花在 guest 键等待；Session 门锁等待中位 1 µs、p95 612 µs，
  键信号到唤醒中位约 0.01 ms，唤醒路径不是瓶颈。播放线程等待的事件由
  解码/合成/显示链上的 guest 线程在约 34 ms（中位）后才发出。
- 这些线程的信号栈落在 `NvMMLite`/`NVOMX`/`Nvx` 流水线代码；剩余约 100–120 ms/帧
  是 guest 多媒体管线在 Vita3K 中的处理与握手延迟，不是本仓库平台钩子。
- 因此原 guest 管线在 Vita3K 内未达到 30 fps 内容更新；框架级原生播片已在第 8 节
  达到 29.974 fps。真机 L4 尚未验证，不能把 Vita3K 的数字外推到 Vita。若继续在
  Vita3K 内优化原 guest 管线，需要替换/加速 guest 多媒体管线或改进模拟器 CPU
  调度，属于平台层之外的独立工程。

## 8. 框架级原生播片结果（2026-11-01）

启用 `native-movie.enable` 后，加载器从 ROM 树读取同一个 MP4，复用原 guest NVDEC
桥创建的 SceAvcdec 解码器，在独立宿主线程解复用/解码/呈现；guest present 被抑制、
guest 音频被静音。完整片头结束前不写游戏状态；结束后写入 `uMovie` 命令 8，并等待
其状态回到 9，让游戏自己的停止/清理路径进入标题。

完整运行（Vita3K v0.2.1 4106-d7edcbe9，OpenGL，540p）：

| 指标 | 观测 |
|---|---|
| VPK SHA256 | `7c78767bf25f2257ccf95b465806b07e932177732bcb1e70dffa09fc895e2699` |
| SELF/eboot SHA256 | `be28aaaf3a1706a5a15dbb3a6b4526d465a36849f9e3f9d8feb885211d577dc2` |
| 影片 | `nativeNX/movie/movie06.mp4`，960×540，5280 样本，176.176 秒 |
| 解码/呈现 | 5280 / 5278（2 帧解码延迟未呈现） |
| 窗口/帧率 | 176.085 秒 / 29.974 内容帧每秒 |
| 结束状态 | t=225 秒标题界面；无进程崩溃 |
| 音频 | 无；guest 音频在原生呈现期间静音 |

截图 t=60/120/180 秒为正常影片画面，t=225 秒为游戏标题；证据在
`build/runs/native-movie-full-20261101/`（不进入 Git）。移除 marker 的对照运行在
70 秒内记录 360 次原 guest 解码，证明回退路径仍工作。另外，单独启用
`movie-force-stop.enable` 的对照在首次解码 5 秒后写入命令 8，t=50 秒已进入标题，
证明该停止命令是游戏自己的退出路径，而不是原生播放伪造的完成状态。

未验证：音频、其他影片/循环/快速切换、带 UI 叠加的过场、真机 L4、长时间稳定性。
原生路径失败时记录 `VP_NATIVE_MOVIE_FAIL` 并回退 guest；不得把 fallback 当成
30 fps 成功。详见 [ADR 0014](decisions/0014-native-movie-player.md)。

## 9. 渲染性能安全迁移（2026-11-02）

本分支（基点 `develop` `08d4b6d`）选择性迁移了旧
`codex/render-performance`（`9f3e810`）提交 `bcd1d3d` 中的两个代码点：

- static pair hint 由 1 项改为 8 项，完整输入比较、`used` 检查和失效/重用清理由
  原路径保留；未扩大到 32 项，未携带 census 或 CPU clear。
- 全部 pending scene drain 时只等待最新通知值，成功后退休更早 pending 及其 upload
  pin；arena 重用等待保留，失败 poison 且不释放资源。通知值跳过 0，最新/退休判断
  使用同一串行号比较，避免 32 位回绕提前释放。

这两项不改 draw/clear/present 顺序、资源内容或像素；旧分支的命中率与等待调用下降
只是历史 L3 数据，不能写成新分支 FPS 加速。L1 宿主测试 29/29 与 L2 构建已独立
复核通过，输入身份检查通过；L3 Vita3K 与 L4 真机尚未执行。方案边界、反例与测量教训见
[渲染性能安全迁移](13-render-performance-lessons.md)，决策见
[ADR 0015](decisions/0015-safe-render-performance.md)。
