# 原游戏内存、纹理生命周期与日志三项验证

2026-11-06 更新：下文是旧 RGBA 字体工作集下的容量结论。新 Alpha8 原生字模后，
[组合复测](21-performance-consolidation.md) 未再证明 128 MiB/idle 提速，推荐关闭，
保留 64 MiB + 日志减负；512/1664 容量策略两侧固定。不要把旧 33.7% 与新组合收益相加。

日期：2026-11-05。基于 `codex/resource-lifecycle-validation`。原稳定安装不替换。
本报告补充 ADR 0030–0032，不能用旧报告的数字替代本轮包和场景验收。

## 已得出的判断

前一轮“128 MiB 预算没收益”没有否定驻留优化。当时实际只分配到约 88 MiB。
本轮进入原游戏内存初始化，把过大的纹理子堆适度缩小，后端终于实际分配齐 128 MiB，
固定村庄四段对照的帧时间下降约 33.8%。重复解码和池回收等待同步减少，原因能对账。

反复 miss 的十张 1024² RGBA8 已全部关联到 `font_festa_00_HQ` 至
`font_festa_09_HQ` 十张字体图集。它们不是十张每帧变化的场景纹理。不过地址会复用，
对象会释放/重载，名字固定也不能证明内容永不修改。当前仍做逐字节 raw 验证。

正常工作日志减少另观察到约 2.0% 改善，是小收益。不能把它和容量实验的百分比直接
相加，因为没有做两者同时开启的独立对照。

所有性能数字是有限 Vita3K L3；L4/L5、全部任务/住宅/流式峰值仍未验证。

## 一、真实大堆和原游戏子堆

默认 guest heap 为 1895 MiB，另有 8 MiB alias、16 MiB stack；原布局的内存池合计
1919 MiB。这里是移植层给原程序提供的模拟器地址/内存布局，不是 PSV 的显存容量。
原 SDK 根据 GetInfo 取得可用总量后调用 SetHeap；原 main 再按固定表创建大子堆。

新控制文件同时改变真正的 kernel memblock、清零范围和 GetInfo/桥区域。原游戏
`main+151CCC` 中已核对 Resource 500、NVNTexture 850、NVNBuffer 200、Shader 100 MiB。
这类预留不能当作已证明的活对象用量。

| 尝试 | 实际行为 | 判断 |
|---|---|---|
| 仅外围 heap=512 MiB | 原 SDK 请求 512 MiB；Resource 等大分配不能满足，随后错误退出；模拟器又发生宿主访问异常 | 启动失败 |
| 仅外围 heap=1536 MiB | 原 SDK 请求 1536 MiB；原子堆容量不变，启动后进入错误退出/UI | 启动失败 |
| heap=1408、NVNTexture=256 MiB | 原纹理 pool 的 nvmap/map 确实变成 256 MiB；能进村，但有明显黑块/缺件和异常大物体 | 图像失败，不统计为提速 |
| heap=1664、NVNTexture=512 MiB | 有限村庄图像正常；后端 128 MiB 全量 backing 得到满足 | 可继续验证的有效候选 |

256 MiB 运行有 19 次 `MAP_REMAP_REJECT`，包括越出基映射的请求。正常容量运行已发生的
remap 范围最高端为 315.125 MiB，256 MiB 连这个范围都容不下。这个最高端不是全部活
字节求和；512 MiB 通过本场景也不等于已经证明全玩法内存上限。

二进制只改两条 MOVT，原分配方法、失败路径和断言保留；原字、1128 B guard、范围和
验证方法见 [ADR 0031](decisions/0031-original-title-memory-capacity.md)。

## 二、终于分配齐 128 MiB 后的整帧对照

有效运行 `build/runs/resource-capacity512-20261105`。全程使用同一个候选包，
heap=1664、原 NVNTexture=512 MiB 固定；只在 mode 4 的 64 MiB 池和 mode 7 的
128 MiB 池之间切换。两模式均走原游戏 root、统一 raw/decoded mapped 策略，未开启
shared/idle resize/deferred clear/cached raw/日志削减。

细分计时从约 300 s 开，有限资源 key 记录先完成；正式窗口 350–410、460–520、
570–630、680–740 s。每个窗口按同一完整快照端点和帧间隔直方图对账，不把包含时间
再加进整帧。

| 窗口 | 池 | 有效帧 | 整帧均值 ms | P95 范围 ms | 实际 backing |
|---|---:|---:|---:|---:|---:|
| 1 | 64 MiB | 416 | 132.339 | 147–148 | 64 MiB |
| 2 | 128 MiB | 672 | 86.951 | 97–98 | 128 MiB |
| 3 | 64 MiB | 352 | 150.552 | 168–169 | 64 MiB |
| 4 | 128 MiB | 576 | 100.490 | 112–113 | 128 MiB |

合并：64 MiB 共 768 帧、140.687 ms；128 MiB 共 1248 帧、93.200 ms，帧时间下降
33.754%。两对下降 34.297% 和 33.253%。NPC 动态和跨窗口耗时有变化，因此只比较
同进程交替窗口，不把本轮 64 MiB 与另一个包的历史均值直接相减。

| 同端点成本/计数（按帧加权） | 64 MiB | 128 MiB | 含义 |
|---|---:|---:|---|
| tex-lookup 自身 ms | 14.317 | 19.667 | 更多命中仍逐字节比较，成本反而增加 |
| tex-store 自身 ms | 1.529 | 0.006 | 反复新建/驱逐大幅减少 |
| tex-decode 自身 ms | 18.689 | 0.288 | 避免重复解码是实收益 |
| wait-notify 自身 ms | 20.685 | 2.515 | 原先部分 GPU 等待实由池压力引起 |
| LOG 自身 ms | 11.410 | 11.272 | 本对照未开启日志削减 |

64 MiB 两段 miss 为 83.58/83.76 次每帧；128 MiB 为 1.006/1.014 次每帧。
raw 比较量从约 235–239 MiB/帧升到约 296.5–296.7 MiB/帧。没有靠少验证内容、
丢 draw 或关闭报错取得收益。总收益还包括别的细项变化，上表不能冒称完整硬件 GPU 时间。

340/450/560/670/750 s 五张同尺寸村庄采样已人工查看，未见 256 MiB 候选那样的新增
黑块、缺件或变形。无运行时读回；图像检查只覆盖这些帧，不代表全部动画。窗口只在
正式窗口前移动位置，不缩放；前台焦点并非锁定，未最小化。进程正常退出，exit=0，
约 767.165 s；保存原安装/配置/marker，存档由受保护副本运行后恢复。

### 关闭细分计时后的复测

`build/runs/resource-probeoff-20261105` 使用最终六点包，300–320 s 仅做有界资源取证，
320 s 后关闭 frame-cost；四段正式窗口中没有细分 span/快照，也不开 play-perf/game-cost。
普通帧间隔、工作日志、拒绝和资源累计记录仍开。因此称“细分探针关闭”，不称完全无日志。

| 窗口 | 池预算 | 帧 | 整帧均值 ms | P95 范围 ms | 实际 backing |
|---|---:|---:|---:|---:|---:|
| 1 | 64 MiB | 416 | 138.732 | 158–159 | 64 MiB |
| 2 | 128 MiB | 608 | 91.737 | 104–105 | 116 MiB |
| 3 | 64 MiB | 384 | 138.446 | 159–160 | 64 MiB |
| 4 | 128 MiB | 608 | 91.952 | 104–105 | 116 MiB |

合并 800/1216 帧，138.595 → 91.844 ms，下降 33.732%；两对下降 33.875% 和 33.583%。
本轮固定在村长另一页较短对话，资源采样包含八张大图集；不能冒称与前一轮十张图集
完全相同，也不能直接用跨轮差值估算探针开销。池按需增长，本轮正式窗口的真实 backing
为 116 MiB，分配失败计数为 0；这证明大于 64 MiB 的充分驻留收益，不宣称本轮用了满 128。

两模式稳态 stage 9 各原因累计值不增长，direct_fail/quarantine 为 0。stage 3 累计拒绝
各段增加 5/16/11/8，按原样保留，不宣称全部 draw 零拒绝；这些少量动态事件与 33.7%
收益的量级不符，且候选第一段拒绝反而更多。五张采样均已查看，无新增黑块/缺件；
均未最小化/缩放，但前台焦点没有锁定。进程 exit=0、约 767.178 s，原存档/安装恢复。

## 三、十张字体图集的原代码生命周期

原容量四点探针运行 `build/runs/resource-owner-default-20261105` 记录 529 次 load-start、
529 次 load-commit 和 3 次显式 release。没有混行/截断；固定村庄资源采样的十张大纹理
全部关联到 `GUI\02_common\font\font_festa_00_HQ` 至 `_09_HQ`。

例如 VA `540C80200` 对应 `_09_HQ`、`540720200` 对应 `_08_HQ`、
`53F1A0200` 对应 `_04_HQ`。这些 VA 只说明这次运行的对应关系，不进入生产白名单。
有界采样排除首尾后有 13 个完整帧，每张每帧一次 miss；有些图集同帧被请求两次。

四点原型的一个真实缺口是：它看见旧图集和重新加载的图集复用同一 VA，却没有看到
所有对象销毁。查原指令后，两个析构函数会内联释放 GPU 对象，绕过显式 release。
因此补齐到六点；没有把四点原型输出的“旧对象仍活着”当作事实。最终六点验证另外
记录，不用名字相同掩盖缺少析构事件。

最终六点运行记录 529 次 load-start、529 次 load-commit、218 次 destroy-delete、
3 次 destroy、3 次显式 release，事件序列连续且无混行/截断。有限采样中的八张大图集
全部对应唯一当前对象；没有把未在该页请求的两张说成已完成同页关联。其资源范围为
`00/02/04/05/06/07/08/09`，仅代表该页实际请求集合；它不能证明所有写入都已被截获。

入口、原字、64 B guard、576 B islands、SP/寄存器/条件标志语义和分析器边界见
[ADR 0032](decisions/0032-original-texture-lifecycle-probe.md)。宿主测试覆盖释放后未知、
地址复用、新旧名字冲突、同名多对象和截断 GPU 快照，未知不会被补成成功关联。

**本轮没有启用“只看版本就跳过 raw 比较”。** 已取得原对象加载/释放的运行证据，
但仍未证明全部 CPU 直接写、原 SDK upload、DMA/copy、GPU 生产和独立纹理对象的写入
都经过这六处。现在把 load 次数叫作完整内容版本会漏写入，不能用它替换逐字节校验。

### 补查：实际像素是否只是字体

2026-11-05 后续离线核对当前运行树的 `nativeNX/loc/arc/resident.arc`，与本机 update
来源逐字节相等，SHA256 为
`66b9b2e5cb201bc1cde3ed89a68e515d42dbbd97d8ab8f687a96101725a4261d`。
逐项解压 `font_festa_00_HQ` 至 `_09_HQ`，用现有 `tex_format.py` 校验 TEX 完整 mip
布局并解开 block-linear。十张均为1024²、RGBA8_UNORM、11级 mip；共110级全部满足：

- R/G/B 每个逻辑像素均严格为255，字形覆盖信息只在Alpha。
- 单独保存8位Alpha、补回 `(255,255,255,A)` 后，与原RGBA逐字节完全一致。
- 已查看本轮涉及的八张顶级Alpha图：内容是密集字形；00另含字母、数字、标点、
  箭头/图形等符号字形。不是场景贴图，也不是只有汉字。

这是锁定运行资源的离线像素证据（L0），比仅凭名称更强，但没有接入GXM或做新性能
验收。像素/PNG/解压文件只在忽略的 `build/font-content-check-20261105`，不提交。
8张顶级decoded单独从RGBA8改为Alpha8可由32降到8 MiB；10张由40降到10 MiB。
这不包含原始raw副本、其他纹理和各级mip，不能把整个缓存池一并算成缩小75%。
后端实验必须还原原采样的RGB=1/Alpha，覆盖原shader、过滤、mip和表示类型/引用管理；
不能直接改格式标志或因此关闭raw验证。

## 后续优化顺序

1. 优先扩大 512 MiB 原纹理子堆候选的场景覆盖，查任务/住宅/切换时的峰值；同时追
   Resource、NVNBuffer 等其他预留，不能把 512 MiB 单场景成功直接变成真机预算。
2. 先试字体decoded的Alpha8专用表示，利用已验证的110级恒白RGB减少驻留压力；另对
   十张字体图集追齐原对象与全部写入/释放，闭合后再试省raw副本/版本复用。
   目前剩余约19.7 ms的raw lookup仍须单独处理，Alpha8不会自动消除它。
3. 正常日志削减可作为独立小收益；GXM/命令处理等仍按新整帧成本选择。不能再沿用
   64 MiB 抖动时的“GPU 等待约 20 ms”去解释已经充分驻留后的帧。
