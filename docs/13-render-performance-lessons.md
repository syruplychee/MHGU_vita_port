## 2. 仅接受的两项优化

### 2.1 static pair hint：1 项改为 8 项

**做法**：保留 `static_pair_hint_probe` 的完整 `static_pair_inputs_match` 比较，只把
“最近一次成功 pair”的单项 hint 改成 8 项、按 age 淘汰的最近命中表。`used` 检查、
slot 身份与完整输入比较全部保留；`static_pair_hint_forget` 在 pair 释放或
重用前清除对应项，reset 清空整表。没有扩到 32 项，没有携带 CPU clear、census 或
任何诊断写入。

**为什么不改变输出**：hint 仍只是“候选 slot 的索引”，不是缓存命中结论。任何候选
都必须通过与原扫描完全相同的完整输入比较；失败就继续扫描，行为与旧路径一致。
hint 不持有引用，slot 释放/重用前会显式失效，因此不会把旧程序或旧状态绑定到新
draw。改变的只有查表顺序和少量 CPU 命中率，不改变 draw 顺序、状态、资源生命周期
或像素。

**旧分支历史数据（仅 L3 参考）**：hint 命中率 51% → 72.8%，pair 每 draw 约
37.8 → 36.6 µs；32 项命中率提高到 88.1%，但 pair 仍约 36.5 µs，没有额外时间收益，
因此旧分支最终保留 8 项。该数据不能写成整帧加速。

### 2.2 `gxm_pending_scene_complete`：一次等待最新 scene

**做法**：同一 GXM context 的 scene 按提交通知值顺序执行。需要全部 drain 时，遍历
pending 找到通知值最新的 scene，只对它做一次 `sceGxmNotificationWait`；成功后用
`retire_upto` 清理所有更早的 pending scene，并按原有语义逐个释放它们持有的 upload
pin。每个 arena 重用前仍调用 `gxm_pending_scene_complete_arena` 单独等待该 arena。
等待失败时保留 pending 与全部 pin，调用 `frame_poison_context` 并返回原始错误。

**通知值比较**：`gxm_notify_next` 统一了递增并跳过 0 的规则（`UINT32_MAX` 之后是
1，不是 0）。最新选择与清理判断使用同一组串行号比较：

- `gxm_notify_newer(a, b)`：无符号差值 `a - b` 非零且小于 `0x80000000`；
- `gxm_notify_reached(completed, pending)`：`!gxm_notify_newer(pending, completed)`。

只支持当前有界流水线：每个 arena 最多一个，共 3 个 pending，arena 重用与同步边界
会持续等待和清理旧工作，通知值差不会跨越 2^31 的半窗口。不得把该 helper 当作通用
时间戳比较。最新判断与 `retire_upto` 使用
严格互补的条件，因此 32 位回绕时不会把尚未等待的新 scene 提前清理。

**为什么不改变输出**：GPU 按提交顺序消费同一 context 的 scene，等待最新通知值即
证明所有更早 scene 已完成；清理只发生在成功等待之后。失败路径不释放 pin，避免 GPU
仍可能读取时复用 staging。改变的是一次 drain 的等待调用次数，不是完成条件。

**旧分支历史数据（仅 L3 参考）**：`notify_calls` 23,071 → 20,555（约 −10.9%），但
`notify_block_us` 约 3.97 → 4.03 秒，没有减少。该等待受 GPU 完成时间限制，不能把
“调用次数下降”写成“完成等待变快”，更不能写成 FPS 提升。

在默认路径采用前需要额外验证。它们没有迁入本分支。

## 5. 测量教训

1. **固定同状态和镜头对话再比较。** 时间驱动回放会让同一墙钟窗口落在不同对话页/
   镜头，甚至白屏；截断回放会因终止释放事件提前结束并进入白屏，追加未来空输入也
   不能恢复。实时输入邮箱能减少漂移，但仍是墙钟驱动；确定性对照应使用帧驱动或
   “确认状态后再计时”。
2. **显存读回不能替代显示采样验证。** 旧 `surface_gpu_blue_probe` 在 present 后读回
   显示缓冲全为 0，因为该后端把颜色留在 host surface；不能据此说采样不可见。后来
   用 GPU 采样两条色带、外部截图逐像素验证清除路径，才同时覆盖了“填写 → 采样 →
   显示”。
3. **计数下降不等于整帧加速。** 通知调用 −10.9% 但阻塞时间不降；纹理复制 −84%
   也没有稳定换来整帧时间。必须区分调用次数、CPU 时间、GPU 阻塞和墙钟帧间隔。
4. **分清 staging、fill 与诊断 copy。** 同一窗口曾把暂存复制、上传缓存填充和跨 VA
   诊断比较混在一起；分离后 16 MiB 为暂存 28.60 GB/7.637 s、填充 153 MB/45 ms、
   诊断 51.7 MB/16.7 ms。混算会直接得出错误结论。
5. **错误 NVN skip 反转推翻过上限判断。** 第一版在 `skip==0`（record）时提前返回，
   `skip==1` 反而执行原绘制。旧 skip 实验中的 33 ms 来自正常路径的 30 FPS 限制，
   不能当作删去绘制后的上限。修正后 record 132.2 ms、skip 33.8 ms，
   33 ms 只是“没有绘制工作”的上界，不是当前实现的帧率。
6. **uniform 跨帧 0 命中是聚合结果。** 多 stage、多 bank 合成一个哈希时，一个矩阵/
   时间字段变化就会让整组零命中；不能据此认定所有 uniform 每帧都变，也不能仅按
   structure 重放旧命令。要按 bank、按 shader 实际使用范围拆分。
7. **旧“必须整帧下降 20% 才继续”的门槛不再是硬约束。** 阴影跳过曾达到 mean −25%，
   后续帧驱动对照却出现负收益，说明门槛不能替代状态控制和可重复性。它仍可作为
   投入排序的参考，但每次都要先证明测量窗口可信。
8. **静态表增长会改变加载地址。** 旧 census 表增加约 43 KiB BSS 后，连续三次把 SDK
   放到离桥接代码超过 A32 ±32 MiB 的位置，启动报 `VP_PATCH_REACH(-6)`。表不大也可能
   影响加载，必须实际启动核对。本次仅扩大 8 项 hint，不迁入大型诊断表，也不修改
   guest 二进制、ABI、补丁范围和原字节；仍需验证模块分配和启动。
9. **98% 的跨帧集合命中不证明命令可以重放。** 它没有验证顺序、资源读写依赖和 pin
   生命周期。`present` 调用约 0.18 ms 也只说明该调用便宜，不能排除 GPU 瓶颈。

### 5.1 剩余瓶颈

旧分支 L3 已定位到的主要成本仍成立，但数值只代表旧窗口：

- guest 命令分发/解码与平台每 draw 准备；旧 285 秒混合窗口曾估计“完全消除 draw
  prep 只从约 8 FPS 到约 9.4 FPS”，但它含嵌套计时与 census 开销，不是稳定村庄
  窗口的受控上限，不能据此否定所有命令缓存。
- 主颜色 pass 占平台 draw 时间约 65.3%，阴影 pass 约 31.0%，其余小目标约 3.7%。
- 最大合成/精灵家族 `0xe69` 约占平台 draw 时间 21.6%，准备主要是纹理/资源工作；
  最大静态网格家族 `0x6d0` 约 9.2%，单家族优化上限不足。
- 纹理解码/上传、完成等待、Vita3K guest CPU 调度和模拟 GXM 调用本身。

### 5.2 下步优先级

2026-11-03 更新：主线改为游戏内部公共渲染提交，具体入口和取证计划见
[内部提交计划](15-engine-render-submission-plan.md)。两词 draw 标记没有提速，只否定
那个原型的收益，未否定上游材质准备、对象队列和阶段入口接管。

1. 以黑块修复版为画面对照，从真实 NVN 返回地址反向追公共入口；先查 `main+0xBC1764`
   的覆盖、已有缓存和上层调用者，按跨家族准备成本选切片。
2. 读清资源写入、局部状态重建、矩阵与材质字段变化后，替换重复准备或命令生成；
   保留游戏原数据，确保对应旧路径不再执行，不依赖旧解码快照维持完整状态。
3. 用固定状态多对整帧 A/B 决定是否扩大接管；队列重排须有顺序/资源依赖证明。
4. 48 MiB 缓存、单副本和阴影降频保留为独立候选，不代替上游主线的完成与否。
5. 真机 L4 重新检验所有 L3 数字；Vita3K 的调度与 GXM 模拟成本不能外推。
